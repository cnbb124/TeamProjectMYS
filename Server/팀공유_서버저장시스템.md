# 서버 저장 시스템 정리 (팀 공유용)

> 게임 세이브를 **내 컴퓨터 파일이 아니라 MySQL DB에 저장**해서,
> 어느 PC에서 접속해도 내 데이터가 유지되게 만드는 작업입니다.
> **서버 몰라도 읽을 수 있게** 정리했어요.

---

## 0. 한 줄 요약

**"게임 저장을 파일 → DB로 옮겼고, 골드가 재접속 후에도 유지되는 것까지 실제 확인 완료.
이제 미니PC를 24시간 공용 서버로 세팅 중 — 팀 전체가 같은 DB를 쓰게 됨."**

> **공용 서버 주소 (강의실 네트워크): `http://192.168.0.8:5080`**
> 유니티 `ServerApi`의 `Server Url`에 이 값이 들어가 있으면 됨.
> (집 등 다른 네트워크에서 접속하려면 Tailscale 필요 — 설정되면 그 주소도 여기 추가 예정)

---

## 1. 왜 필요한가?

지금 게임은 저장하면 내 PC에 `save0.json` 파일로 저장됨. 문제 두 가지:
- 다른 PC에서 하면 내 세이브가 없음
- 파일 열어서 골드 999999로 고치는 치트 가능

그래서 저장을 한 곳(DB)에 모으는 구조로 변경:

```
[유니티 게임] ──"저장해줘"+데이터──▶ [API 서버] ──SQL──▶ [MySQL DB]
   (손님)                          (은행 창구)          (금고)
```

**게임이 DB에 직접 안 붙고 서버를 거치는 이유**: 게임 파일은 유저 PC에 깔려서
누구나 뜯어볼 수 있음. 거기에 DB 비밀번호를 넣으면 금고 열쇠를 손님한테 주는 꼴.
그래서 열쇠는 서버만 갖고, 게임은 서버한테 부탁만 함.

---

## 2. 용어 사전 (이 문서에서 쓰는 비유들)

이 문서는 전체를 **은행 비유**로 설명합니다. 먼저 이야기로 들으면:

> 여러분(= 게임)이 귀중품(= 세이브 데이터)을 은행에 맡기러 갑니다.
> 은행에 가면 금고에 직접 들어가는 게 아니라 **창구 직원**한테 맡기죠.
> 직원(= 서버)은 "이 물건 진짜 맞아요?" 확인하고, **금고**(= DB)에 넣어줍니다.
> 금고 안에는 물건 종류별로 **서랍**(= 테이블)이 나뉘어 있고요.
> 나중에 다시 오면(= 재접속) 직원이 금고에서 꺼내 돌려줍니다.
> 이때 내 것을 찾으려면 **사물함 번호**(= userId)가 필요합니다.
> 손님한테 금고 열쇠를 직접 주는 은행은 없습니다. 그게 서버가 필요한 이유예요.

이 이야기를 기억하고 아래 대응표를 보면 됩니다:

| 비유 | 실제 용어 | 뜻 |
|---|---|---|
| **금고** | DB (데이터베이스, MySQL) | 모든 유저의 데이터가 보관되는 곳 |
| **서랍** | 테이블 (table) | 금고 속 엑셀 시트. 같은 종류 데이터끼리 모아둠 (예: 계정 서랍, 골드 서랍) |
| **은행 창구 (직원)** | API 서버 | 게임의 부탁("저장해줘")을 받아 금고에 넣고 꺼내주는 중간 프로그램 |
| **창구 하나하나** | 엔드포인트 (예: `/save`, `/login`) | 부탁 종류별로 창구가 따로 있음 |
| **쪽지** | JSON | 데이터를 글자로 적은 형식. 예: `{ "gold": 500 }` |
| **금고 명령어** | SQL | 창구 직원이 금고를 다룰 때 쓰는 전용 언어 |
| **비밀번호 다지기** | 해시 (BCrypt) | 비번을 원문 대신 알아볼 수 없게 뭉개서 저장. 일방통행이라 되돌릴 수 없음 → DB 털려도 안전 |
| **고유번호 / 사물함 번호** | userId | 가입하면 발급되는 내 번호. 저장/로드가 전부 이 번호에 묶임 |

## 3. 단계별로 만든 것

### 1단계 — DB 설계 (`Server/schema.sql`)
금고 안에 서랍(테이블) 6개를 설계:

| 서랍(테이블) | 담는 것 |
|---|---|
| `users` | 계정 (아이디, 비밀번호) |
| `player_save` | 레벨/경험치/HP/실드/골드 + extra_json(호감도·스킬 쪽지) |
| `part_slot` | 장착 파츠 |
| `missile_slot` | 미사일 + 탄약 |
| `inventory_item` | 인벤토리 (게임 쪽 PlayerLoadout 구현되면 사용) |
| `item_master` | 아이템 사전 (추후 검증용, 아직 비어있음) |

### 2단계 — API 서버 (`Server/Api/Program.cs`, C# / ASP.NET)
창구 6개를 만듦:

| 창구 | 하는 일 |
|---|---|
| `/health` | 서버 살아있니? |
| `/db/ping` | DB에 연결되니? |
| `/register` | 회원가입 (비밀번호는 다져서 저장) |
| `/login` | 로그인 → 내 고유번호(userId) 발급 |
| `/save/{userId}` | 게임의 SaveData 쪽지를 통째로 받아 금고에 나눠 저장 |
| `/load/{userId}` | 금고에서 꺼내 SaveData 모양 그대로 돌려줌 |

### 3단계 — 유니티 연결 (`Assets/2.Scripts/Network/`)

| 파일 | 역할 |
|---|---|
| `ServerApi.cs` | 서버와 통신하는 전담 스크립트 (가입/로그인/저장/로드) |
| `TestServerSave.cs` | 테스트용 키 (F5 저장 / F6 골드+100 / F9 로드) — 검증 끝나면 삭제 예정 |
| `ServerApi.prefab` (`Assets/3.Prefabs/Network/`) | 위 두 스크립트 + 서버주소/자동로그인이 세팅된 프리팹. **씬에 이거 하나만 드래그**하면 준비 끝 |

> ※ **GameManager 등 공용 코드는 건드리지 않았습니다.** 서버 저장은 위 스크립트/프리팹만으로 **독립 동작**해요. (게임의 정식 저장 흐름과의 통합은 저장 흐름이 확정된 뒤 별도로 진행)

### 4단계 — 실제 검증 (완료)
```
유니티에서 F6으로 골드 900 적립 → F5 저장 → 플레이 완전 종료
→ 다시 플레이 → F9 로드 → 골드 900 복원 ✅
MySQL 안에도 gold=900 실제로 박혀있는 것 확인 ✅
```

## 4. 알아야 할 것 (중요)

- 서버 저장은 **`ServerApi` 프리팹을 자기 씬에 넣은 사람만** 쓰는 독립 기능입니다.
- **GameManager 등 공용 코드는 수정하지 않았음** → 서버 안 써도, 몰라도 여러분 작업에 아무 영향 없음.
- 게임의 정식 저장 흐름(STATION 씬)과의 통합은 저장 흐름이 확정된 뒤 별도로 진행 예정.

**건드리면 안 되는 것:**
- `git reset --hard`로 동기화 금지 (포톤 지워지는 사고 남) → **merge/pull로만**

## 5. 사용된 프로그램 (뭘로 만들었나)

| 프로그램 | 역할 (비유) | 비고 |
|---|---|---|
| **MySQL Server 5.7** | 금고 그 자체. PC 뒤에서 항상 돌아가는 프로그램 | 학원 수업 때 쓴 그 MySQL |
| **MySQL Command Line Client** | 금고에 명령 내리는 마이크 (SQL 입력) | MySQL 설치하면 같이 깔림 |
| **.NET 9 SDK** | 창구 직원(C# 서버)을 실행시키는 엔진 (`dotnet run`) | 마이크로소프트 무료 배포 |
| **유니티 (UnityWebRequest)** | 게임이 서버에 전화 거는 도구 | 유니티 내장 기능이라 설치 불필요 |

서버 코드는 **C# (ASP.NET)** — 유니티에서 매일 쓰는 그 C#이라 별도 언어 공부 없이 만듦.

### 아파치(Apache) 아니에요.

수업에서 서버를 **아파치(Apache)** 로 배웠는데 이 서버는 아파치가
아니라 **C#/.NET에 내장된 웹서버(Kestrel)** 로 돌아갑니다. 서버 쪽만 설명 :

- **아파치 방식**: 웹서버 프로그램을 따로 설치 → 설정 파일(httpd.conf, 가상호스트 등)을
  손보고 → 그 위에 PHP/HTML을 올리는 구조. 웹서버와 내 코드가 **별개**.
- **.NET 방식 (우리 것)**: 웹서버가 **코드 안에 이미 들어있음.** 그래서 아파치 설치도,
  설정 파일도 없이 `dotnet run` 한 줄이면 서버가 켜집니다. 포트 같은 것도 설정 파일이
  아니라 실행할 때 옵션(`--urls http://0.0.0.0:5080`)으로 줘요.

그래서 **아파치 때 하던 것 중 여기선 안 하는 것**: 웹서버 설치, httpd.conf/가상호스트
설정, 문서 루트(DocumentRoot) 지정 같은 게 전부 없습니다. "무엇을 응답할지"는 전부
`Program.cs`(C# 코드) 안에 창구(엔드포인트) 형태로 적혀 있어요.

반대로 **아파치든 뭐든 똑같이 해야 하는 것**도 있어요: 남의 PC에서 접속하게 하려면
방화벽에서 포트(5080)를 열고, 서버 PC의 IP를 알려주는 것 — 이건 웹서버 종류와 상관없는
공통 작업입니다.

> 한 줄 비유: 아파치는 "건물(웹서버)을 빌려서 그 안에 내 코드를 넣는 것", .NET은
> "내 코드 안에 서버가 이미 붙어 있어서 실행만 하면 되는 것". 그래서 세팅이 오히려 더 단순합니다.

**아파치로 작업했을 때 슈팅게임이나 FPS는 사용하기 어렵다는 점이 있어서, 닷넷으로 작업하게 되었습니다.**

#### 아파치로 슈팅 게임을 못 만드는 결정적 이유

아파치(Apache HTTP Server)는 태생이 "문서 전달용 프로그램"입니다.

- **아파치의 작동 방식**: 클라이언트가 "우주선 A 위치 보낸다!" 하고 요청하면, 아파치는 "알았다!"
  하고 연결을 즉시 끊어버립니다. (웹서버 vs 소켓서버의 차이) 아파치는 일회성 요청/응답에만 특화되어 있습니다.
- **실시간 게임의 필요조건**: 나와 친구, 그리고 적 20마리의 위치가 1초에 수십 번씩 갱신되어야 하므로,
  연결이 절대 끊어지지 않고 계속 뚫려 있어야 합니다(소켓 통신).
- 만약 아파치로 억지로 2인용 슈팅 게임을 만들면, 내 화면에서 적을 쐈는데 친구 화면에는
  1~2초 뒤에 적이 죽는 심각한 렉(Delay)이 발생합니다.

## 6. 내 PC에 처음 세팅하는 법 (1회만)

> ※ **이제 미니PC(공용 서버)가 생겼습니다.** 팀원 대부분은 이 세팅을 할 필요가 없어요 —
> 유니티 `Server Url`을 공용 서버 주소(`http://192.168.0.8:5080`)로 두면 바로 사용 가능.
> 아래 과정은 **혼자 오프라인으로 서버까지 뜯어보고 싶은 사람**만 참고하면 됩니다.

### ① 프로그램 설치 (없다면)
- **MySQL Community Server** — mysql.com에서 다운로드. 설치 중 **root 비밀번호**를 정하는데, 팀 통일로 `1234` 권장 (헷갈림 방지)
- **.NET 9 SDK** — dotnet.microsoft.com에서 ".NET 9.0 SDK" 다운로드/설치

### ② 금고(DB) 만들기 + 설계도 적용
`MySQL Command Line Client` 열고 (비밀번호 입력) 아래 명령:
```sql
CREATE DATABASE teamprojectmys CHARACTER SET utf8mb4;
```
그다음 명령 프롬프트(cmd)에서 설계도(schema.sql) 로드:
```
"C:\Program Files\MySQL\MySQL Server 5.7\bin\mysql.exe" -u root -p teamprojectmys < (소스트리에서 받은 경로)\Server\schema.sql
```
(MySQL 버전에 따라 폴더명 `MySQL Server X.X` 부분은 다를 수 있음)

### ③ 서버에게 금고 열쇠 주기 — appsettings.json 만들기
`Server/Api/` 폴더 안에 `appsettings.json` 파일을 새로 만들고 아래 내용 입력:
```json
{
  "ConnectionStrings": {
    "MySql": "server=localhost;port=3306;user=root;password=1234;database=teamprojectmys"
  }
}
```
- `password=` 뒤는 ①에서 정한 본인 MySQL 비밀번호
- ⚠️ 이 파일은 **비밀번호가 들어있어서 git에 안 올라감** → PC마다 직접 만들어야 함

### ④ 확인
아래 "서버 켜기" 하고 브라우저에서 `http://localhost:5080/db/ping` →
`{"db":"connected"}` 뜨면 세팅 끝.

## 7. 직접 해보고 싶을 때 — 사용법

### ① 서버 켜기 (명령 프롬프트)
```
예시 : cd C:\TeamProjectMYS\Server\Api  // 소스트리에서 받은 Server\Api 자신의 경로로 명령 프롬프트로 해주세요.
경로 설정 후 
dotnet run --urls http://localhost:5080 입력 후 엔터
```
- 이 창을 켜둔 동안만 서버가 살아있음 (닫으면 꺼짐)
- 브라우저에서 `http://localhost:5080/db/ping` → `{"db":"connected"}` 뜨면 정상

### ② 유니티 세팅 (1회만)
1. `Assets/3.Prefabs/Network/ServerApi.prefab` 을 **자기 씬에 드래그** (ServerApi + TestServerSave + 서버주소/자동로그인 다 세팅돼 있음)
   - 프리팹 없이 직접 하려면: 빈 오브젝트에 `ServerApi` + `TestServerSave` 부착 → `Auto Login On Start` 체크 → `Server Url`에 서버 주소 입력
2. **(처음 한 번) HTTP 연결 허용** — `Edit → Project Settings → Player → Other Settings →
   "Allow downloads over HTTP"` 를 `Allowed in development builds`(권장)로 변경

> **HTTP 연결 설정 메모 (중요)**
> 서버가 `http://`(암호화 안 함)라서 유니티가 기본적으로 연결을 막습니다(“Insecure connection not allowed”). 위 5번 설정으로 허용.
> - 이 설정은 **프로젝트 공용(`ProjectSettings.asset`)이라, 한 명이 바꿔서 올리면 팀 전체에 적용**됩니다. (개인 설정 아님)
> - `Allowed in development builds`: 에디터·개발빌드에선 http 허용, 정식 릴리즈(.exe) 빌드에선 자동 차단(안전). 개발 중엔 다 에디터에서 하므로 이 값으로 충분.
> - 릴리즈 .exe로 서버에 붙여야 하면 `Always allowed`로 바꾸거나 https 필요.
> - 보안: http는 내부망/테스트용. 공개 서비스가 아니라 팀 내부(강의실 LAN + Tailscale)라 위험은 낮음. 나중에 https가 필요하면 Tailscale 인증서 기능(`tailscale cert`)이 사설 IP 환경에 현실적 (Let's Encrypt는 공인 도메인이 있어야 해서 사설 IP엔 부적합).

### ③ 테스트 (플레이 중, Game 화면 클릭 후)

|---|---|
| F6 | 골드 +100 |
| F5 | 서버에 저장 |

시연 코스: **F6×3 → F5 → 플레이 정지 → 재플레이 → F9 → 골드 복원 확인**

### ④ DB(금고) 직접 구경 (선택)
시작메뉴 → `MySQL 5.7 Command Line Client` → 비밀번호 `1234`

## 8. 우리 코드에 미리 준비되어 있던 것들 (설계 부분)

이번 서버 작업을 하면서 확인해 보니, **처음 코드를 설계할 때부터
네트워크/DB를 염두에 둔 내용**으로 만들었으며 실제로 큰 도움이 됐습니다.

### ① ID(고유번호) 기반 설계
`enum_IDs.cs`에 이렇게 적혀 있음:
> "저장/로드, **네트워크 전송**, DB PK 용도로 사용."

모든 아이템/스킬이 고유번호(int)로 관리되는 구조라서:
- **DB 저장**: 파츠 에셋 통째가 아니라 번호만 저장 → 이번 작업이 수월했던 핵심 이유
- **네트워크**: 나중에 "미사일 2001번 발사!"처럼 번호만 보내면 됨
- (D3D의 핸들, DB의 기본키와 같은 원리 — "무거운 실체 대신 가벼운 번호로 가리킨다")

### ② 발사 구조가 멀티플레이 정석 방식에 맞음
- 모든 투사체가 `WeaponSystem.Shoot() → Init(위치, 방향, 쏜사람)` **단일 입구**로 발사됨
- 총알/미사일은 `PoolManager`에서 재활용 (풀링)

→ 멀티에서 총알을 하나하나 중계하면 통신량이 폭발하는데, 정석 해법은
**"발사 정보(번호+위치+방향)만 알리고(RPC), 각자 게임이 자기 풀에서 꺼내 쏘는 것.**
우리 구조가 이미 딱 그 모양이라, 포톤 작업 때 큰 수술 없이 붙일 수 있음.

### ③ 일시정지를 Time.timeScale로 안 함
멀티에서 timeScale 정지는 못 씀 (내가 멈춰도 남의 게임은 돌아가므로).
우리는 `IsPaused` 플래그 방식이라 이 문제가 없음.

### ※ 참고: 포톤과 이 문서(DB 저장)는 별개
| | DB 저장 (이 문서) | 포톤 (다음 작업) |
|---|---|---|
| 비유 | 은행 (귀중품 보관) | 단체 통화방 (실시간 중계) |
| 하는 일 | 골드/파츠 보관, 재접속 시 복원 | 다른 플레이어 위치/발사 실시간 공유 |
| 상태 | ✅ 완료·검증됨 | 서버 연결 테스트만 됨, 본 작업 미착수 |
