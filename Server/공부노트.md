# 서버 공부노트 (TeamProjectMYS)

> 게임 세이브를 서버 + DB에 저장하는 작업을 이해하기 위한 노트.
> 모르는 게 나오면 여기부터 다시 읽자.

---

## 1. 큰 그림 (이거 하나가 전부)

```
 [유니티 게임]  ──① JSON──▶  [API 서버]  ──② SQL──▶  [MySQL DB]
  (클라이언트)               (C#, 창구)               (금고)
       ▲                                                  │
       └──────────────── ③ 로드 = 반대로 다시 꺼냄 ────────┘
```

- **① 저장**: 게임이 세이브 데이터를 JSON(쪽지)로 만들어 서버에 보냄
- **② 기록**: 서버가 SQL(명령어)로 DB에 씀
- **③ 로드**: 재접속하면 반대로 DB → 서버 → 게임 순으로 다시 꺼내옴

---

## 2. 은행 비유

| 실제 | 비유 |
|---|---|
| 유니티 게임 | 손님(나). 귀중품(세이브)을 맡기고 싶음 |
| API 서버 | 은행 창구 직원 |
| MySQL DB | 금고 |

**왜 게임이 DB에 바로 안 붙고 서버를 거칠까?** (제일 중요)
- 게임 파일은 플레이어 PC에 있어서 누구나 뜯어봄.
- 거기에 DB 비밀번호(금고 열쇠)를 넣으면 = 손님한테 금고 열쇠를 줌 → 해킹당함.
- 그래서 **창구(서버)가 중간에서 검증**한다. (예: "이 골드 진짜 맞아?")

---

## 3. 용어 사전

| 용어 | 쉬운 뜻 |
|---|---|
| 클라이언트 | 손님 쪽 = 유니티 게임 |
| 서버 | 요청을 받아 처리해주는 중간 프로그램 = 창구 |
| API | 서버가 열어둔 "창구들"의 총칭 |
| 엔드포인트 | 창구 하나하나. `/save`, `/load`, `/login` |
| 요청/응답 | "저장해줘"(요청) → "됐어"(응답) |
| JSON | 데이터 쪽지 형식. 예: `{ "gold": 500 }` (이름:값) |
| SQL | 창구 직원이 금고(DB)에서 쓰는 전용 명령어 |
| 테이블 | 금고 속 엑셀 시트 (예: player_save) |
| 행(row) | 가로줄 = 플레이어 1명의 데이터 |
| 열(column) | 세로칸 = 항목 하나 (예: gold 칸) |
| 관계형 | 항목마다 칸을 따로 만드는 정석 정리법 |
| connection string | 금고 주소 + 열쇠 (서버가 DB에 붙는 접속정보) |
| UnityWebRequest | 유니티가 서버에 전화 거는 도구 |
| Kestrel | .NET에 내장된 웹서버. `dotnet run` 하면 켜지는 그것 (아파치 자리) |

---

## 3-1. 아파치 배웠는데 이건 왜 달라요? (Kestrel / .NET)

수업에서 배운 서버 = **아파치(Apache)**. 우리 서버 = **C#/.NET의 Kestrel**.
둘 다 "웹 요청 받아 응답하는 서버"인 건 같은데, 만드는 방식이 다르다.

| | 아파치 | .NET (우리 것) |
|---|---|---|
| 웹서버 | 따로 설치하는 별도 프로그램 | C# 코드 안에 내장(Kestrel). 따로 설치 안 함 |
| 설정 | httpd.conf 등 설정 파일 편집 | 코드 / 실행 옵션(`--urls`)으로 지정 |
| 실행 | 아파치 서비스 시작 | `dotnet run` 한 줄 |
| 내 코드 두는 곳 | 문서 루트에 PHP/HTML 올림 | `Program.cs`의 엔드포인트로 작성 |

- 아파치의 "설치 → 설정파일 → 올리기"가 .NET에선 **`dotnet run` 한 줄**로 압축됨.
- 방화벽 포트 열기·IP 알려주기는 아파치든 .NET이든 외부 공개할 때 **공통**.
- (참고: 실서비스에선 아파치/Nginx를 앞에 세우고 Kestrel을 뒤에 두는 "리버스 프록시"
  구성을 쓰기도 하지만, 우리 팀 규모(내부망 소수)에선 Kestrel 단독으로 충분.)

---

## 4. 저장 방식 = 하이브리드

금고 정리법 두 가지를 섞는다:

- **관계형 컬럼** (골드·파츠·미사일): 서버가 **검증·계산**할 것 → 칸을 따로 만든다.
- **JSON 컬럼** (호감도·스킬·앞으로 추가될 것): 그냥 보관만 → 쪽지째 한 칸에.
  - 장점: 새 항목이 생겨도 금고 구조(테이블)를 안 바꿔도 됨.

**한 문장 규칙:**
> 서버가 들여다봐야 하면 **컬럼**, 그냥 맡아두기만 하면 **JSON**.

(현업에서도 이 하이브리드를 많이 쓴다. "JSON은 현업에서 안 쓴다"는 반은 오해 —
 다만 골드처럼 검증할 값을 통짜 JSON에만 두면 해킹에 취약해서, 그런 건 컬럼으로 뺀다.)

## 7. 직접 실행/테스트 하는 법

```bash
# 1) 서버 켜기
cd Server/Api
dotnet run --urls http://localhost:5080

# 2) 브라우저에서 열기
http://localhost:5080/health    → {"status":"ok"}  (서버 살아있음)
http://localhost:5080/db/ping   → {"db":"connected","users":0}  (DB 연결됨)
```

- MySQL CLI 위치: `C:\Program Files\MySQL\MySQL Server 5.7\bin\mysql.exe`
- DB 이름: `teamprojectmys`
